## Находки и исправления

### SEC-01 — уязвимые зависимости тестового инструментария

`vitest@3.2.6` / `@vitest/mocker` затронуты
[GHSA-82fw-gwwq-j7x9](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9).
В цепочке присутствовал `tinypool`, отмеченный npm как critical по
GHSA-5gmw-xhrv-c9v3 и GHSA-85c8-ppgw-ccpr. Серьёзность npm относится к пакетам;
эксплуатация production BookTrack этими проверками не установлена.

Vitest обновлён и зафиксирован на **4.1.11**: эта исправленная версия поддерживает
используемые Vite 6 и Node 24. `tinypool` ушёл из дерева зависимостей.
Lock-файл обновлён, 112 тестов и чистая установка прошли. После обновления
критических записей npm audit нет. `npm audit fix --force` не применялся.

Установленный npm 9 при обновлении завершился внутренней ошибкой `edgesOut`;
установка повторена совместимым npm 11 через локальный кэш, без глобальной замены npm.

### SEC-02 — оставшиеся зависимости Tailwind 3

Полный аудит всё ещё завершается ненулевым кодом: **5 high и 2 moderate**.
Это семь пакетов одной цепочки сборки, а не семь независимо доказанных атак:
`braces`, `chokidar`, `micromatch`, `fast-glob`, `postcss-selector-parser`,
`postcss-nested`, `tailwindcss`.

Основные advisory:

- [braces: stack-exhaustion DoS](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm);
- [PostCSS selector parser: CPU exhaustion](https://github.com/advisories/GHSA-rj75-hqrm-r3gf).

На дату проверки последняя опубликованная `braces` — 3.0.3 — затронута advisory.
Для selector parser исправлена версия 7.1.6, но Tailwind 3 использует ветку 6.
Рекомендация npm переводит Tailwind на другую основную версию. Принудительные
подмены несовместимых транзитивных пакетов и миграция CSS в рамках этого исправления
не выполнялись; находки **остаются открытыми**.

В этом проекте шаблоны glob и CSS берутся из доверенных файлов репозитория;
пользовательские названия книг и заметки поступают в runtime и не передаются
компилятору Tailwind. Эти пакеты не включены в production-зависимости приложения.
Это ограничивает применимость, но не отменяет риск для сборки/CI при обработке
недоверенных изменений. Dev-сервер привязан к 127.0.0.1; PR не получает deployment-секретов.
Рекомендуется отдельно запланировать проверяемую миграцию Tailwind, ограничивать
источники кода и повторять аудит при обновлениях.

### SEC-03 — email/password не требует подтверждения адреса

Публичный `/auth/v1/settings` подтвердил `mailer_autoconfirm=true`:
новая email/password регистрация не доказывает владение адресом. GitHub Provider
и email/password включены. Это реальный остаточный риск идентификации владельца email.

Настройка не изменялась автоматически. Перед включением Confirm email нужно
проверить существующую доставку почты в Dashboard: стандартный SMTP Supabase
ограничен адресами команды проекта и не предназначен для общей production-рассылки.
[Ограничения SMTP](https://supabase.com/docs/guides/auth/auth-smtp),
[Confirm email](https://supabase.com/docs/guides/auth/general-configuration).
Другой сервис самостоятельно не подключался. Текущее приложение уже умеет показывать
ожидание подтверждения, если Supabase вернёт пользователя без сессии.
По решению пользователя проверка Custom SMTP, настройка почты и включение
Confirm email пропущены. В рамках этапа 6 письма регистрации, восстановления
пароля и почтовые тесты не отправлялись; такие действия не выполняются без новой
инструкции пользователя. Настройки Auth и существующий email/password вход
сохранены. Наличие Custom SMTP не проверено; SEC-03 остаётся открытым риском.

### SEC-04 — отсутствовали защитные заголовки frontend

Production-ответ до исправления не содержал X-Frame-Options, Referrer-Policy,
X-Content-Type-Options и CSP. HSTS уже выдаётся Vercel.
В `vercel.json` подготовлены `DENY`, `no-referrer`, `nosniff` и CSP
`frame-ancestors 'none'; object-src 'none'; base-uri 'self'`.
Они ограничивают встраивание, плагины, подмену base URL и передачу Referer.
Это **частичная CSP**, без ограничения script-src, а не полная защита от XSS.
Загрузка подготовленной Метрики и GitHub OAuth этими директивами не запрещены.
После публикации все четыре заголовка подтверждены на frontend и `/api/health`;
сам endpoint возвращает 200 и три checks=up. Vercel Logs подтверждены владельцем;
Supabase API Gateway и успешный вход в Auth Logs подтверждены владельцем.

### SEC-05 — прежние собственные диагностические записи не были JSON

`backendError` раньше выводил префикс и объект operation/category. Утечки секретов
в этой записи не обнаружены; отсутствовал требуемый единый формат.
Добавлен общий logger с фиксированными event/message и допустимыми полями.
Health Check получает серверный UUID и возвращает его в `X-Request-Id`;
этот же requestId записывается в JSON. Значение заголовка клиента не переиспользуется.
Корреляция и отбрасывание чувствительных/произвольных полей проверены тестами.

## Логирование и воспроизводимый анализ с Codex

Схема собственной записи: `timestamp`, `level` (`info`, `warning`, `error`),
`event`, `message`, при наличии — `requestId`. Дополнительные поля ограничены
operation/category, HTTP status, числовой durationMs, фиксированными checks и reason.
Переданные Error/stack, URL, headers, пароль, токен, email, user ID и данные книги
не сериализуются. Поля и сообщения не берутся из пользовательского ввода.

| Источник | Где смотреть |
|---|---|
| Vercel Function | Vercel → проект → Logs, фильтр `/api/health`; JSON выводится через console.info/warn/error |
| Frontend backend.failure | DevTools → Console; эти записи не отправляются в Vercel автоматически |
| Supabase | Dashboard → Logs / Logs Explorer, Auth и API/PostgREST; собственный backend работает в Supabase |

Используются [Vercel Logs](https://vercel.com/docs/functions/logs) и
[Supabase Logs](https://supabase.com/docs/guides/observability/logs), внешнего
сервиса логирования нет. Платформенные записи/сообщения SDK могут иметь собственный
формат и служебные метаданные. Доступ к кабинетам ограничен владельцем;
сырые экспорты не нужно публиковать в Git или передавать Codex.

**Демонстрационные данные:** [logs.demo.jsonl](audit/logs.demo.jsonl) — три явно
синтетические записи, включая искусственный тайм-аут БД. Они не доказывают
production-инцидент. Воспроизведение:

```sh
node scripts/analyze-logs.mjs docs/audit/logs.demo.jsonl
```

Фактический результат: 3 записи, по одной info/warning/error, две health.completed,
одна backend.failure, один database=down. Анализатор выводит только счётчики
разрешённых событий, а не исходные сообщения и идентификаторы.

**Реальные данные:** [logs.local-real.jsonl](audit/logs.local-real.jsonl) — одна
запись локально запущенной скомпилированной функции, проверившей настоящие зависимости.
Результат: HTTP 200, requestId совпал с заголовком ответа, три checks=up.
Это не журнал Vercel и не подтверждение публикации нового logger.

```sh
node scripts/analyze-logs.mjs docs/audit/logs.local-real.jsonl
```

Воспроизводимый запрос Codex:

> Проанализируй docs/audit/logs.demo.jsonl и результат scripts/analyze-logs.mjs.
> Посчитай уровни и события, выдели отказавшую зависимость. Не выводи сырые записи,
> не делай вывод о production-инциденте по демонстрационным данным.

Codex реально выполнил анализатор при подготовке отчёта. Интерпретация демо:
ошибка относится к тайм-ауту SQL-пробы, при доступных frontend и Auth; warning
означает невозможность авторизовать чтение списка и сам по себе не доказывает атаку.
Для реального расследования нужны соседние обезличенные записи и Dashboard.
Перед передачей реальных экспортов удалить токены, OAuth code, параметры URL,
cookies, email, IP и пользовательские данные; секреты не вставлять в prompt.

## Остаточные риски и ожидаемые проверки

- SEC-02: семь dev-записей npm audit не исправлены; не обрабатывать недоверенные
  glob/CSS и не публиковать dev-сервер в сеть.
- SEC-03: email autoconfirm включён; проверка и настройка почты отложены по
  решению пользователя. Новый почтовый сервис не выбирался, отправка писем не запускалась.
- Supabase SDK хранит сессию в browser storage; успешная XSS могла бы её прочитать.
  React escaping и частичная CSP уменьшают отдельные риски, но не исключают XSS.
- Сканирование Git ограничено доступной локальной историей, выбранными шаблонами
  и известными локальными значениями; это не доказательство отсутствия любых секретов.
- Административные настройки Supabase/Vercel, retention, rate limits и доступы
  не считывались через административные токены.
- Защитные HTTP-заголовки подтверждены на production, JSON info/warning в Vercel Logs
  подтверждены владельцем. В Supabase API Gateway подтверждён HTTP 200 SQL-пробы;
  успешный вход в Auth Logs также подтверждён владельцем.
  Нет подтверждения полного production-пентеста.
- Яндекс.Метрика сохранена, но настройка/реальная доставка событий отложены
  по решению пользователя. ДЗ6 целиком не объявляется завершённым.

Статусы: **Готово и проверено** — перечисленные локальные тесты, npm-проверки,
live RLS, публикация, production HTTP-заголовки и ручная проверка Vercel Logs
и Supabase API Gateway / Auth Logs в их заявленных границах.
**Не выполнено** — исправление SEC-02,
отложенная по решению пользователя проверка/устранение SEC-03.
