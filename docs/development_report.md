До работы в репозитории были только `docs/` и `.git`: не было package.json,
приложения, компонентов и автоматических тестов. Изучены исходная формулировка ДЗ4,

Минимум ДЗ4 в ТЗ — просмотр, добавление и поиск. Текущий запрос требует frontend MVP;
раздел 6 ТЗ разрешает остальные операции раньше ДЗ5 на mock-этапе.
Реализованы все семь согласованных функций. Это не расширяет продуктовый MVP:
нет новых полей, каталога, обложек, статистики и социальных функций.
БД, Auth/RLS, API, Supabase, постоянное хранение отложены до ДЗ5.
Исторические артефакты и незавершённый A/B-эксперимент ДЗ2 не переписывались.

## 3. Этапы разработки

1. Прочитаны документы и проверена фактическая структура. Изображение концепции
   использовано как визуальный референс, не как доказательство работающего интерфейса.
2. Создана основа React/TS/Vite и Tailwind. Версии выбраны для имеющегося Node 18.15.
   Итоговые Vite 6.4.4 и Vitest 3.2.6 декларируют Node 18 в собственных package.json.
   При первичном выборе изучена документация [Vite 6](https://vite.dev/blog/announcing-vite6)
   и [Vitest](https://v3.vitest.dev/guide/). Точные версии фиксирует lockfile.
3. Вынесены Book, BookInput, union BookStatus, русские подписи, trim/валидация,
   совместный поиск/фильтр и сортировка created_at DESC, id ASC.
4. Реализован mock-адаптер в памяти: UUID, ISO UTC, копии возвращаемых записей,
   сохранение created_at при update; отсутствующий id не вызывает создание.
5. Созданы библиотека, карточка, общая форма и подтверждение удаления.
   Форма сохраняет ввод после отказа; успех появляется только после resolve.
   Синхронная блокировка исключает повтор до обновления disabled в React.
6. Настроены позитивные и негативные тесты, затем проведён рефакторинг повторяющейся
   обработки pending/error. Фактические результаты проверок приведены ниже.

## 6. Контракты и состояния

- Пять редактируемых полей, длины после trim 200/120/1000 по UTF-16 string.length.
- rating=null либо целое 1–5 только для finished; уход из finished очищает оценку
  с пояснением и не восстанавливает её автоматически.
- list: loading → success/empty/error; ошибка приоритетнее пустой поисковой выдачи.
- create/update/remove: pending → success/error; блокируются повтор и отмена;
  ошибка до записи не меняет библиотеку и не сбрасывает форму.
- После записи условия поиска сохраняются; скрытая ими книга сопровождается
  пояснением и действием сброса.
- Подтверждение показывает название; отмена ничего не удаляет. Начальный фокус
  на отмене; после удаления — заголовок библиотеки.
- Native dialog обеспечивает модальность; форма фокусирует первое поле/ошибку,
  после закрытия фокус возвращается к открывшему элементу, если он остался в DOM.
- Слой данных не зависит от React. При замене на Supabase потребуются серверная
  проверка данных, Auth/RLS и обработка неоднозначного исхода сети из ТЗ ДЗ5.
- Отказы mock происходят до изменения массива, поэтому повтор безопасен именно
  в рамках этой модели. Постоянство и многопользовательская изоляция не заявляются.

## 9. Рефакторинг и ограничения при сдаче

После первой реализации убрана дублирующаяся обработка pending/error/блокировки
из формы и подтверждения: выделен `useAsyncAction`. В `Dialog` сосредоточен жизненный
цикл native modal и возврат фокуса. Общие статусы и валидация используются и формой,
и mock-слоем; создание и редактирование используют одну форму. Отдельный безопасный
класс ошибки недоступной книги позволяет показать её текст без вывода сырых исключений.
Поиск остаётся простым проходом по массиву; отдельное глобальное хранилище и мемоизация
без измеренной необходимости не добавлялись.

Предусмотрен локальный запуск, разрешённый оригиналом вместо деплоя.
Публикация репозитория и сдача на учебной платформе требуют действий владельца:

- [ ] Ссылка GitHub из существующего origin: https://github.com/sergogaset/BookTrack .
  Новые файлы в этом сеансе не закоммичены и не отправлены; владелец должен опубликовать их перед сдачей.
- [ ] При необходимости URL деплоя: **не выполнялся; локальный запуск описан в README**.
- [ ] Приложить дополнительные ручные доказательства из раздела 8 и отправить работу.

Окончательное решение «Принято» принадлежит преподавателю; отчёт не подменяет
оставшиеся проверки утверждением о полном прохождении всех NFR или серверных AC.
