# Пошаговая декомпозиция: форма добавления книги

[Навигация](README.md) · [Контекст](project_description.md) · [Технические требования](technical_specification.md) · [Правила](rules.md) · [RTCF](prompt_templates.md)

Это демонстрация техники промтинга для будущего ДЗ4. Шаги ниже не выполнялись в коде в рамках ДЗ2.

## 1. Исходный общий запрос

> Сделай форму добавления книги.

## 2. Почему запрос недостаточно точен

Не указаны поля, типы, пределы ввода, связь оценки со статусом, способ сохранения, отмена, состояния и критерии готовности. Агент может добавить ненужную БД, придумать структуру проекта или сбросить данные после ошибки. Не определены доступность и проверка результата.

## 3. Уточнённая постановка

На этапе ДЗ4 в существующей основе React + TypeScript + Vite создать форму добавления BookTrack с Tailwind CSS. До реализации изучить фактические файлы и [правила](rules.md). Если основы нет, обозначить недостающий контекст; не разворачивать приложение в рамках этой задачи.

Вход BookInput: title, author, status, rating, notes. title после trim — 1–200 символов, author — 1–120, notes — до 1000 (пустая -> null). Статусы: want_to_read («Хочу прочитать», по умолчанию), reading («Читаю»), finished («Прочитано»). rating — null или целое 1–5 только при finished; при переходе в другой статус очищается до null с пояснением. Длины считаются через JavaScript string.length.

Контракт формы: onSave(input: BookInput): Promise<void>, onCancel(): void. Родительский mock-слой в памяти назначает UUID и ISO-времена UTC, добавляет книгу один раз; user_id отсутствует до ДЗ5. Повторная отправка и отмена блокируются на pending. Reject сохраняет ввод, показывает ошибку, возвращает действия. Resolve закрывает/сбрасывает форму; родитель объявляет успех. Отмена вне pending не вызывает сохранение. После перезагрузки mock data сбрасываются. Supabase и новые зависимости не нужны.

## 4. Декомпозиция на семь этапов

Промпты выполняются последовательно в одной задаче с переданными документами. Критерий перехода — проверка результата этапа, а не обязательное повторное разрешение владельца на каждый шаг. При провале проверки исправить текущий этап.

### Этап 1. Проверить основу и контракт

**Цель:** определить место формы и избежать дублирования типов.

```text
Изучи BookTrack, docs/project_description.md, docs/technical_specification.md и docs/rules.md. Найди основу
frontend, типы, UI и тестовые scripts. Без изменений опиши контракт BookInput,
onSave(input): Promise<void>, onCancel(): void и минимальный список файлов.
Укажи, кто назначает id/created_at/updated_at. Если основы нет, сообщи об этом;
не создавай приложение. Перечисли допущения и проверки следующих шагов.
```

**Ожидаемый результат:** список реально найденных файлов, план и контракт пяти редактируемых полей; служебные поля принадлежат mock-слою.

**Переход:** основа существует, контракт согласован с контекстом; отсутствующие prerequisites явно обозначены и устранены отдельной задачей ДЗ4.

### Этап 2. Подготовить поля и доступную структуру

**Цель:** создать управляемую форму без логики БД.

```text
По контракту этапа 1 добавь BookForm: title, author, select status,
необязательные rating и notes. Начальные значения: пустые строки,
want_to_read, пустая оценка. Добавь label, уникальные id, button submit
«Сохранить», button type=button «Отмена», видимый фокус. Оценка доступна
только при finished. Используй существующие элементы и Tailwind;
не добавляй зависимости. Сохранение подключается на следующем этапе.
```

**Ожидаемый результат:** поля доступны по подписям, клавиатурой можно пройти всю форму, status содержит ровно три значения.

**Переход:** значения меняются без предупреждений React, отмена не отправляет форму, структура не включает служебные поля.

### Этап 3. Валидировать и нормализовать ввод

**Цель:** исключить невалидный BookInput.

```text
Добавь в BookForm общую нормализацию и валидацию по контексту:
trim title/author/notes; длины 1–200, 1–120, до 1000 соответственно;
пустая notes -> null. status — только три значения BookStatus.
Пустая rating -> null; иначе целое 1–5 при finished. При смене finished
на иной статус очисти rating и объясни это текстом. Свяжи ошибки с полями
через aria-describedby/aria-invalid; при неверной отправке фокусируй первое
неверное поле. Не передавай ошибочный ввод в onSave и не очищай поля.
```

**Ожидаемый результат:** нормализованный вход либо ошибки конкретных полей; пустая оценка не становится нулём.

**Переход:** проверены пробельные поля, границы длин, rating null/1/5/0/6/дробь и сброс оценки при смене статуса.

### Этап 4. Подключить асинхронное mock-сохранение

**Цель:** обеспечить создание ровно одной книги без backend.

```text
Подключи onSave(BookInput): Promise<void> к родительскому mock-слою в памяти.
Назначай UUID, created_at и updated_at (одинаковое ISO UTC время при создании).
Не добавляй user_id или Supabase. На pending блокируй повторную отправку
и отмену, показывай «Сохранение…». На resolve добавляй книгу один раз,
закрывай/сбрасывай форму, объявляй успех у родителя через role=status.
На reject сохрани ввод, покажи понятное сообщение через role=alert,
верни повтор и отмену. Не объявляй успех до завершения Promise.
```

**Ожидаемый результат:** успешная запись появляется в списке один раз; управляемые mock resolve/reject демонстрируют переходы состояния.

**Переход:** двойной клик не дублирует запись; reject не добавляет книгу и сохраняет ввод; повтор после отказа успешен.

### Этап 5. Завершить отмену и проверить интерфейс

**Цель:** обеспечить предсказуемый выход и адаптивность.

```text
Проверь onCancel: вне pending закрывает форму без onSave и без новой записи;
во время pending недоступен. После повторного открытия новая форма пустая
со статусом want_to_read. Проверь Tab, Enter, видимый фокус, связь ошибок,
объявление результата и длинный ввод на 320/768/1280 CSS-пикселях.
Исправь локальные проблемы переноса и доступности, не меняя архитектуру.
Отдельно перечисли фактически выполненные и недоступные ручные проверки.
```

**Ожидаемый результат:** отмена не создаёт запись, сообщение успеха не исчезает вместе с формой, нет горизонтального переполнения.

**Переход:** доступность и размеры проверены либо оставшиеся проверки явно отмечены как невыполненные; не считать этап полностью принятым при существенном пробеле.

### Этап 6. Проверить автоматическими тестами

**Цель:** закрепить пользовательские сценарии.

```text
Используя имеющиеся Vitest и React Testing Library, добавь минимум три
содержательных теста BookForm: (1) невалидные обязательные поля блокируют
onSave и показывают ошибки; (2) корректный нормализованный ввод сохраняется
один раз; (3) reject сохраняет ввод и разрешает повтор. Дополнительно покрой
pending, отмену, границы rating и его сброс при смене статуса.
Используй управляемые Promise и запросы по role/label; реальная сеть не нужна.
Запусти фактический script проекта. Если окружения нет, не устанавливай
зависимости, сообщи ограничение и не заявляй об успешных тестах.
```

**Ожидаемый результат:** тесты и отчёт о выполнении с командами и результатами, дефекты исправлены в пределах задачи.

**Переход:** доступные тесты проходят; незапущенные проверки не считаются пройденными.

### Этап 7. Проверить diff и оформить результат

**Цель:** завершить ограниченное и обозримое изменение.

```text
Сопоставь форму с FR-02, FR-05, FR-08–FR-10 и NFR из контекста.
Проверь diff, доступную проверку типов, тесты и сборку согласно scripts.
Удали только собственные ненужные изменения, не затрагивая работу владельца.
Кратко зафиксируй контракт и mock-ограничения. Перечисли изменённые файлы,
команды с фактическими результатами, оставшиеся ручные проверки и резюме.
```

**Ожидаемый результат:** отчёт с доказательствами, минимальный diff и документированные ограничения хранения в памяти.

**Переход:** чек-лист ниже выполнен; невыполненные пункты явно препятствуют объявлению полной готовности.

## 5. Финальный объединённый промпт

```text
Ты frontend-разработчик BookTrack. В существующей основе ДЗ4 реализуй только
форму добавления книги. Прочитай docs/project_description.md, docs/technical_specification.md и docs/rules.md,
изучи реальные типы/UI/scripts. Если frontend отсутствует, сообщи об этом
и не создавай всё приложение. Дай краткий план и явные допущения.

Последовательно выполни семь этапов: контракт; доступные поля; валидация;
mock-сохранение; отмена/адаптивность; тесты; итоговая проверка diff.
BookInput: title (trim, 1–200), author (trim, 1–120), status
(want_to_read/reading/finished; по умолчанию want_to_read), rating
(null или целое 1–5 только при finished), notes (trim, до 1000; пустая -> null).
Длины — string.length. При смене finished на другой статус очисти rating
до null с пояснением. Контракт: onSave(input): Promise<void>, onCancel(): void.
Родительский mock-слой в памяти назначает UUID и ISO UTC времена;
created_at=updated_at при создании. Никаких Supabase, user_id и новых зависимостей.

Label/связанные ошибки, фокус к первому неверному полю, видимый фокус;
проверить 320/768/1280 px. На pending блокировать повтор и отмену;
reject сохраняет ввод и возвращает действия; resolve добавляет запись
один раз, закрывает/сбрасывает форму, родитель объявляет успех.
Отмена вне pending ничего не сохраняет. Данные сбрасываются при перезагрузке.

Минимум три автоматических теста: невалидный ввод, успешное сохранение,
ошибка с сохранением ввода; дополнительно pending, отмена, rating и смена статуса.
Запусти доступные тесты, типизацию и сборку согласно scripts, проверь diff.
В конце: файлы, фактические результаты команд, ограничения и ручные проверки.
Не выдавай план или непроведённую проверку за выполненную работу.
```

## 6. Чек-лист приёмки будущей реализации

- [ ] Основа и существующие типы изучены; нет дублирования модели.
- [ ] Есть все пять полей и ровно три статуса с русскими подписями.
- [ ] Обязательность, trim, длины и допустимые оценки проверяются.
- [ ] Пустая оценка — null; вне finished оценка очищается с пояснением.
- [ ] Ошибки связаны с полями, клавиатура и фокус работают.
- [ ] Pending исключает повтор и отмену; reject сохраняет ввод и допускает повтор.
- [ ] Resolve добавляет одну запись, назначает служебные поля и объявляет успех.
- [ ] Отмена вне pending не сохраняет; новое открытие имеет начальные значения.
- [ ] На 320/768/1280 px нет переполнения; длинный ввод не скрывает действия.
- [ ] Минимум три автоматических теста реально запущены и прошли.
- [ ] Доступные проверки типов и сборки прошли; ограничения указаны.
- [ ] Нет БД, авторизации, новых зависимостей и функций вне MVP.

Чек-лист намеренно не отмечен: это критерии будущей реализации, а не результаты ДЗ2.
