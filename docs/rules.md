# Практические правила Codex для BookTrack

[Навигация](README.md) · [Описание проекта](project_description.md) · [Технические требования](technical_specification.md)

Правила применяются к будущим задачам разработки; в ДЗ2 создаётся только документация.

## Роль

AI-агент — разработчик React/TypeScript и аналитик BookTrack; изучает фактические файлы и сообщает проверяемые результаты.

## Контекст

Продукт — [project_description.md](project_description.md), FR/NFR и контракты — [technical_specification.md](technical_specification.md). Архитектура: UI отделён от mock-слоя на ДЗ4, адаптер Supabase и RLS добавляются в ДЗ5.

## Стиль кода

Именование компонентов и типов — PascalCase, переменных и функций — camelCase; имена полей данных сохраняют согласованный контракт. Следовать форматированию существующего проекта. Комментарии объясняют нетривиальное решение, а не повторяют код. Общие типы и русские подписи статусов не дублировать.

## Ограничения

Запрещено обходить типизацию через any, раскрывать секреты и подключать БД на mock-этапе. Не расширять MVP без задачи. Конкретные правила и примеры приведены в RULE-01–RULE-15 ниже.

## Формат результата

Краткий проверяемый план, изменения по фактической структуре проекта, результаты реально выполненных проверок и оставшиеся ограничения. Не выдавать ожидаемые результаты за проведённые эксперименты.

## Практические правила
| ID и название | Правило | Зачем нужно | Правильное применение в BookTrack |
| --- | --- | --- | --- |
| RULE-01 — Изучить проект | До изменения прочитать относящиеся к задаче файлы, инструкции и git diff; назвать фактически найденные типы и компоненты | Не строить решение на вымышленной структуре | Перед BookCard проверить наличие Book; если кода нет, сообщить об этом и не утверждать, что компонент уже существует |
| RULE-02 — Соблюдать MVP | Реализовывать только поставленную функцию и текущий учебный этап | Предотвратить рост объёма | Для карточки показать название, автора и статус; не подключать обложки или внешние API |
| RULE-03 — Типизировать | Использовать TypeScript, union статусов и явные пропсы; не скрывать ошибки через any | Ловить неверные данные и контракты | BookStatus допускает только want_to_read, reading, finished; onEdit принимает id: string |
| RULE-04 — Упрощать архитектуру | Разделять UI и сохранение небольшим контрактом; не вводить слои без задачи | Сохранить понятность учебного проекта | Форма вызывает onSave(input): Promise<void>; Supabase не импортируется в поля формы |
| RULE-05 — Переиспользовать | Сначала искать подходящие типы, поля и отображения; выделять общий код при реальном повторении | Избежать расхождения логики | Добавление и редактирование используют одну BookForm и одну карту русских подписей статусов |
| RULE-06 — Валидировать ввод | Проверять trim, длины, status и rating по контексту; не терять ввод при ошибке | Не допустить некорректной книги | Для пробельного title показать ошибку; при смене finished на reading очистить rating до null с пояснением |
| RULE-07 — Показывать состояния | Для асинхронных действий явно описывать loading/error/success, для списка также empty | Пользователь должен понимать результат действия | На сохранении блокировать повтор и отмену; при ошибке сохранить поля; «нет книг» отличать от «нет совпадений» |
| RULE-08 — Обеспечить доступность | Использовать семантические элементы, label, клавиатуру, видимый фокус и связанные ошибки | Дать доступ к функциям без мыши и цвета | Статус карточки содержит текст; ошибки формы связаны через aria-describedby, результат объявляется через status/alert |
| RULE-09 — Проверять адаптивность | Проверять 320/768/1280 CSS-пикселей и длинный текст | Не допустить потери действий на узком экране | Длинное название в BookCard переносится, кнопки не выходят за границы |
| RULE-10 — Тестировать поведение | Добавлять значимые тесты сценариев и границ; не ограничиваться snapshot | Проверять пользовательский результат | Проверить запрет пробельного автора, успешную отправку и сохранение ввода после reject |
| RULE-11 — Защищать данные | Не хранить секреты в коде/логах; не исполнять HTML заметок; на ДЗ5 проверять владельца через RLS | Защитить библиотеку и учётные данные | Не добавлять service-role ключ в frontend; проверить запрет чтения чужой книги двумя сессиями |
| RULE-12 — Менять минимально | Ограничить diff задачей, не переписывать соседние файлы и не добавлять зависимости без необходимости и согласования | Облегчить проверку и сохранить работу владельца | При исправлении поиска не форматировать весь проект и не менять форму |
| RULE-13 — Проверять и честно отчитываться | Запустить доступные релевантные проверки, посмотреть diff; указать команды, результат и непроверенное | Отличать предположение от подтверждения | Если Vitest не настроен, указать «тесты не запускались» и причину вместо «всё проходит» |
| RULE-14 — Согласовывать разрушение | До удаления пользовательских данных, сброса истории или разрушительной миграции получить явное разрешение на конкретное действие | Исключить невосстановимую потерю | Не выполнять очистку таблицы books ради теста; использовать изолированные фикстуры, а нужное удаление предварительно согласовать |
| RULE-15 — Документировать решения | Фиксировать значимые контракты, ограничения и изменения поведения кратко и рядом с проектной документацией | Сохранить общий контекст следующих этапов | Записать решение rating=null вне finished и отложенное подключение user_id на ДЗ5 |

## Как использовать правила в запросах

Этот Markdown-файл сам по себе не становится системной инструкцией агента. Явно передайте его текст в контекст запроса либо подключите через поддерживаемый в вашей среде механизм инструкций, предварительно проверив, что агент получил содержимое. Не полагайтесь только на упоминание имени файла, если агент не имеет к нему доступа.

Пример запроса для будущего ДЗ4:

```text
Прочитай docs/project_description.md, docs/technical_specification.md и docs/rules.md как контекст этой задачи.
Примени RULE-01–RULE-15 в пределах задачи формы добавления книги.
Сначала назови найденные файлы и допущения, дай краткий проверяемый план.
Реализуй только согласованный объём ДЗ4 с mock data; БД не подключай.
В конце перечисли изменения, выполненные проверки и ограничения.
Если документы недоступны, сообщи об этом до реализации.
```

Для короткого запроса можно включить нужные правила целиком и указать их ID. Для сравнения A/B передавайте правила только запуску B по [протоколу](testing.md). Просите проверяемый план и выводы, не скрытую внутреннюю цепочку рассуждений.
