# BookTrack — техническое задание

[Навигация](README.md) · [Продукт](project_description.md) · [Истории и AC](user_stories.md) · [UI](ui_concepts/ui_description.md)

## 1. Общая информация

Учебный проект BookTrack, редакция ДЗ3 от 15.10.2026. Это спецификация будущего приложения; код, БД, тесты приложения и деплой в рамках ДЗ3 не создаются. Продуктовое описание хранится отдельно; здесь определены проверяемые контракты. Требования FR-01–FR-11 и NFR-01–NFR-07 перенесены из прежнего project-context.md с сохранением значений идентификаторов.

## 2. Цель и назначение

Обеспечить личный учёт планируемых, читаемых и прочитанных книг с поиском и управлением записями. Критерий результата разработки — выполнение связанных AC, а не число сгенерированных компонентов.

## 3. Целевая аудитория

Регулярный и возвращающийся читатель — персоны US-01–US-07, одна роль с одинаковыми правами. На ДЗ5 пользователь работает исключительно со своей библиотекой. Служебная роль Supabase не является пользовательской ролью приложения.

## 4. Границы MVP

Список, добавление, редактирование, подтверждаемое удаление, смена статуса, поиск и фильтрация. Необязательные оценка и заметка входят в общую форму книги. Исключены жанры, ISBN, обложки, внешние каталоги, социальные функции, рекомендации, платежи, сложная статистика, админпанель. Счётчики Dashboard — необязательное представление существующих данных, не отдельное требование.

Решения ДЗ3: лимиты 200/120/1000 подтверждены как учебные ограничения; rating=null вне finished; дубли названия/автора допустимы; поиск без транслитерации, нечёткого сопоставления и приравнивания «е»/«ё». ДЗ4 не требует постоянного хранения, Auth и OAuth2.

## 5. Стек

VS Code + Codex + ChatGPT; React + TypeScript + Vite; Tailwind CSS; Vitest + React Testing Library. ДЗ5: Supabase PostgreSQL + Auth + RLS и клиент Supabase. Репозиторий GitHub, размещение Vercel; финал — GitHub Actions. Playwright возможен позднее при обоснованной необходимости. Версии и зависимости выбираются при реализации, в ДЗ3 ничего не устанавливается.

## 6. Архитектура по этапам

### ДЗ4 — локальный frontend

UI → небольшой типизированный слой данных → mock-массив в памяти. Компоненты: библиотека, карточка, строка поиска, общая форма книги и, на последующем этапе, фильтр и подтверждение удаления. Конкретные пути файлов определяются после создания основы; сейчас их нет. Глобальное хранилище и отдельный backend не требуются.

Планируемый контракт слоя: `list(): Promise<Book[]>`, `create(input: BookInput): Promise<Book>`, `update(id: string, input: BookInput): Promise<Book>`, `remove(id: string): Promise<void>`. В ДЗ4 обязательны list/create, остальные операции реализуются в ДЗ5 либо раньше при сохранении границ mock-этапа. Для тестов задержка и отказ управляются явно, без реальной сети и случайности. Данные сбрасываются после перезагрузки, LocalStorage не требуется.

Форма: `initialValues?: BookInput`, `onSave(input: BookInput): Promise<void>`, `onCancel(): void`. Родитель адаптирует результат слоя данных к Promise<void>, связывает редактирование с id и обновляет список только после успеха. Карточка: `book: Book`, `onEdit(id: string): void`, `onDelete(id: string): void`; сама не обращается к хранилищу и не подтверждает удаление.

### ДЗ5 — реальные данные

UI → тот же контракт → адаптер Supabase → PostgreSQL `books`, Auth и RLS. Supabase предоставляет CRUD API; отдельный сервер и дополнительные предметные таблицы не нужны. Адаптер выполняет проверку структуры ответов во время исполнения: TypeScript не валидирует сетевые данные. Ошибки приводятся к категориям validation / unauthenticated / unavailable / network / unexpected; UI получает безопасное сообщение, не сырой ответ.

Список выбирает книги текущего владельца; RLS защищает и прямые запросы. Поиск и фильтр применяются к полному загруженному списку собственной библиотеки на клиенте. Пагинация и серверный поиск не требуются; при их добавлении контракт нужно пересмотреть, иначе поиск по одной странице будет неполным.

### Финальное ДЗ

Добавляются CI/CD, OAuth2, аналитика, аудит безопасности, мониторинг и структурированное логирование. Это последующий этап, не предварительное условие ДЗ4.

## 9. Модель данных

Одна предметная таблица `books`; таблицами пользователей управляет Supabase Auth. Новые поля не вводятся.

| Поле | Mock / PostgreSQL | Ограничения |
| --- | --- | --- |
| id | string UUID / uuid | Уникальный первичный ключ, не редактируется |
| title | string / text | trim, 1–200, обязательное |
| author | string / text | trim, 1–120, обязательное |
| status | BookStatus / text с CHECK | Только want_to_read, reading, finished; NOT NULL, default want_to_read |
| rating | number или null / integer NULL | null либо 1–5 при finished; при другом статусе только null |
| notes | string или null / text NULL | trim, до 1000; пустая → null |
| created_at | ISO 8601 UTC string / timestamptz | Назначается при создании, сохраняется при update |
| updated_at | ISO 8601 UTC string / timestamptz | Назначается при создании и обновлении |
| user_id | В ДЗ4 отсутствует / uuid NOT NULL с ДЗ5 | Владелец из Auth; связь с auth.users, RLS по auth.uid() |

BookInput содержит только title, author, status, rating, notes. Для update id передаётся отдельно. С ДЗ5 Book расширяется обязательным user_id; роли и права не помещаются в книгу. Дубли title/author разрешены.

Длины считаются как JavaScript string.length (UTF-16), как было определено в ДЗ2. На ДЗ5 эквивалентную серверную проверку нужно предусмотреть явно: PostgreSQL char_length считает Unicode иначе, прямое равенство не гарантируется. Например, символ вне BMP занимает две единицы UTF-16; тесты должны включать такие строки. Нормализация trim на клиенте и сервере использует одинаковую семантику пробельных символов, а не только удаление ASCII-пробела. Это контракт будущей миграции, не заявление о готовой SQL-функции.

Пустое UI-значение rating преобразуется в null. При уходе из finished форма очищает оценку; сырой серверный запрос с rating вне finished отклоняется ограничением. На ДЗ5 БД назначает UUID/времена, обеспечивает запрет подмены created_at/user_id при обновлении. Время хранится UTC; если показывается пользователю, отображается в его локальном часовом поясе. Сортировка задана в FR-01; требований к отдельному экрану статистики нет.

## 10. Пользовательские интерфейсы

Основа ДЗ4 — Minimal Library, [описание и сравнение](ui_concepts/ui_description.md).

- Библиотека: BookTrack, «Добавить книгу», подписанное поле поиска, фильтр «Все» и три статуса; адаптивная сетка карточек. В обязательном объёме ДЗ4 фильтр можно добавить позднее.
- Карточка: title, author, текстовый status, необязательные notes/rating по правилам модели; действия редактирования и удаления появляются при реализации соответствующих функций. Изображения концепций показывают полный целевой MVP.
- Общая форма: title, author, status, условное rating, notes; «Сохранить» и «Отмена». Допустима доступная модальная форма; на mobile занимает доступную ширину с вертикальной прокруткой. Перед первым вводом focus на title; при ошибке — на первом неверном поле; после закрытия — на открывшем элементе.
- Подтверждение удаления: название выбранной книги, «Удалить», «Отмена»; начальный фокус на безопасной отмене. На pending закрытие и повтор блокируются; после удаления фокус переходит к следующей карточке либо заголовку библиотеки.
- ДЗ5: вход/регистрация, выход и истечение сессии. ДЗ4 эти экраны не реализует. Необязательно выделять отдельные маршруты для CRUD, достаточно одного основного экрана.

## 11. Обработка ошибок и Edge Cases

Обозначения: S — чтение списка/результата, W — запись. Общие классы E-01–E-06 ниже являются обязательной частью каждой применимой строки, а не необязательной рекомендацией.

| Функция | Happy path | Валидация | Отсутствие данных | Сеть | Нет сессии | Чужая запись | Неожиданный ответ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| FR-01 просмотр | Карточки после loading | Ответ проверяется по модели, неверный → E-06 | Приглашение добавить первую | E-02 S | E-03 | E-04 S | E-06 |
| FR-02 добавление | Новая запись после успеха | E-01 у поля, не отправлять | Пустая библиотека допустима, книга создаётся | E-02 W, сверка до повтора | E-03 | Подмена user_id → E-04 W | E-06, сверка результата |
| FR-03 редактирование | Обновлена та же книга | E-01, исходник сохранён | E-05, не выполнять upsert | E-02 W, черновик сохранён | E-03 | E-04 W | E-06 |
| FR-04 удаление | Удалён выбранный id | Нет полей; некорректный id → E-05 | E-05, обновить список | E-02 W, сверить отсутствие | E-03 | E-04 W | E-06 |
| FR-05 статус | Обновлён status и условный rating | E-01; неверный enum/rating | E-05 | E-02 W, не показывать новый статус как сохранённый | E-03 | E-04 W | E-06 |
| FR-06 поиск | Вхождение title ИЛИ author | Любой текст допустим, trim; спецсимволы — обычный текст | «Ничего не найдено» либо пустая библиотека | Локальный поиск сети не требует; при отказе исходной загрузки E-02 S | E-03 при исходной загрузке/истечении | E-04 S на источнике; чужих книг в поиске нет | E-06 на источнике |

| E-04 | Запрещён чужой доступ | RLS не возвращает чужие строки. UI: «Книга недоступна», обновление списка; не сообщать, существует ли чужой id. Подмена владельца отклоняется БД |
| E-05 | Выбранная запись отсутствует | «Книга недоступна»/«Книга уже недоступна» при удалении, обновить список, не восстанавливать запись через create. Сохранить черновик редактирования до закрытия |
| E-06 | Неверный формат ответа/неизвестный status/несоответствие сохранённой книги | Не принимать результат как валидный, не объявлять успех; «Не удалось обработать ответ», предложить обновление. Не исполнять/показывать сырой HTML ответа или stack trace |

Supabase/RLS может вернуть пустую выборку или ноль изменённых строк вместо буквального 403. Адаптер проверяет число и форму возвращённых записей; отсутствие и чужая запись намеренно неразличимы. У update проверяется ровно одна возвращённая книга; delete подтверждается возвращённым id, ноль строк обрабатывается через E-05.

ДЗ4 имитирует loading, отказ до записи и успешный повтор в mock-слое; не утверждает наличие работающей сети или защиты. ДЗ5 проверяет реальные Auth/API/RLS и E-01–E-06. При неоднозначном результате create автоматический повтор запрещён: совпадение title/author не доказывает дубликат, так как дубли разрешены. После сверки списка читатель решает, повторять ли ввод; отдельный протокол идемпотентности в MVP не проектируется.

### Другие пограничные случаи

- Повторный клик во время pending не вызывает новую операцию. Обновление списка не заменяет несохранённый ввод формы.
- После успеха активные поиск/фильтр сохраняются; если книга скрыта ими, сообщение успеха предлагает сброс. Удаление последней книги переводит список в empty.
- При конкурентных изменениях одной книги принимается последнее успешно сохранённое изменение; версионирование и слияние вне MVP. Отсутствующая запись никогда не создаётся через update.
- При смене статуса finished → другой → finished прежняя оценка автоматически не восстанавливается. Отмена формы оставляет исходную книгу нетронутой.
- notes с `<script>` отображается обычным текстом; длинное слово переносится. Пустые notes не показываются.
- Ошибка повторной загрузки не подменяется пустым массивом; ранее загруженные свои данные можно оставить с явным сообщением, но при истечении сессии их нужно скрыть.

## 12. Авторизация и безопасность

На ДЗ5 Supabase Auth обеспечивает регистрацию, вход, выход и сессию; OAuth2 не требуется до финального ДЗ. RLS для SELECT/INSERT/UPDATE/DELETE допускает действия только при auth.uid()=user_id; для INSERT/UPDATE необходима проверка новых значений владельца. Изменение владельца через UI или прямой запрос запрещено. Непроверенному user_id из формы доверять нельзя.

Ограничения NOT NULL/CHECK и серверная нормализация обеспечивают инварианты независимо от frontend. Ключ service-role и секреты провайдера не попадают в frontend, репозиторий или логи. Публичный клиентский ключ используется только с RLS и не заменяет проверку доступа. Пользовательский текст не вставляется через HTML. Журналы не содержат токены, пароли и содержимое личных заметок. Инфраструктурные настройки origin/redirect/CORS проверяются при интеграции; отдельный API только ради CORS не создаётся.

Проверки доступа выполняются двумя обычными пользователями и анонимным клиентом, без привилегированного обхода RLS. В финале — аудит, OAuth2, проверка зависимостей и логирование. Конкретные настройки SDK сверяются с актуальной документацией при реализации; здесь подключения нет.
