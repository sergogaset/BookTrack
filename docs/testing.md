# BookCard: сравнение до и после структурирования промпта

[Навигация](README.md) · [Контекст](project_description.md) · [Технические требования](technical_specification.md) · [Правила](rules.md) · [RTCF](prompt_templates.md)

## Статус и границы эксперимента

**Эксперимент не проведён. Оценок и фактических выводов пока нет.** В этой сессии нет доступного механизма двух независимых вызовов модели с управляемым одинаковым стартовым контекстом. Два ответа внутри текущего диалога получили бы уже известные правила и требования и не были бы независимым сравнением. Компоненты и временные реализации в проекте не создавались.

Ниже подготовлен воспроизводимый протокол. Сравнивается одна задача: **«Создать компонент BookCard для отображения книги»**. Гипотеза: явные требования могут улучшить соответствие результата целевому контракту. Гипотеза не считается подтверждённой заранее.

## Эксперимент A — до правил

Передать только базовый запрос, без документов ДЗ2:

```text
Создай React-компонент карточки книги для приложения BookTrack
```

## Эксперимент B — после правил

Передать следующий промпт, а также содержимое project_description.md, technical_specification.md и rules.md как отдельный явно приложенный контекст:

```text
R — Role: Ты frontend-разработчик React + TypeScript учебного BookTrack.

T — Task: Создай BookCard для отображения одной книги. Сначала изучи
выданную основу, дай краткий проверяемый план и явные допущения.
Изменяй только компонент и относящиеся к нему тесты в изолированной копии.

C — Context: Используй приложенные project_description.md, technical_specification.md и rules.md.
Особенно применяй RULE-01 (анализ), RULE-02 (MVP), RULE-03 (типы),
RULE-04 (простота), RULE-05 (переиспользование), RULE-08 (доступность),
RULE-09 (адаптивность), RULE-10 (тесты), RULE-11 (безопасный вывод текста),
RULE-12 (минимальный diff), RULE-13 (проверка).
Этап ДЗ4, React/TypeScript/Vite/Tailwind, mock data. Переиспользуй общий Book:
id: string, title: string, author: string,
status: 'want_to_read' | 'reading' | 'finished', rating: number | null,
notes: string | null, created_at: string, updated_at: string.
user_id до ДЗ5 отсутствует. Данные на входе соответствуют модели;
новую валидацию формы и загрузку данных в карточку не добавляй.
Props: book: Book, onEdit: (id: string) => void,
onDelete: (id: string) => void. Не используй any и не дублируй Book.
Покажи название, автора, текстовую подпись статуса:
want_to_read — «Хочу прочитать», reading — «Читаю», finished — «Прочитано».
Оценку показывай только при finished и rating !== null, например «Оценка: 4 из 5».
Непустую notes выводи безопасным текстом; null/пустую не показывай.
Кнопки редактирования и удаления вызывают соответствующий callback с book.id.
Подтверждение удаления выполняет родитель; карточка сама ничего не удаляет.
Используй article с заголовком, button type=button, доступные имена кнопок
с названием книги, видимый фокус, управление клавиатурой. Цвет не заменяет текст.
Длинные title/author/notes должны переноситься на 320/768/1280 CSS-пикселях.
Loading/error/empty списка обрабатывает родитель, а не карточка одной книги.
Не добавляй ISBN, обложки, жанры, внешние API, БД и зависимости.

F — Format: Краткий план и допущения; код компонента и тестов в пределах основы;
тесты трёх статусов, отсутствия/наличия оценки и заметки, callbacks с верным id.
Используй Vitest + React Testing Library и существующие scripts. В отчёте
перечисли файлы, фактические команды/результаты, ручные проверки адаптивности,
ограничения и итоговое резюме. Не объявляй незапущенные проверки успешными.
```

## Контроль стартовых условий

1. Вне основного проекта подготовить минимальную безопасную основу React + TypeScript с одним общим Book, Tailwind, настроенными Vitest/React Testing Library и scripts. Для эксперимента на ДЗ2 ничего не устанавливать в BookTrack; при отсутствии готовой среды отложить запуск.
2. Создать две одинаковые временные копии основы; сохранить исходный снимок/хеши. В копиях не должно быть пользовательских данных, секретов, этих документов или автоматически подключаемых проектных правил. Одинаковый общий Book доступен обоим запускам.
3. Открыть две новые независимые сессии одного инструмента и одной модели. Зафиксировать точное отображаемое имя модели, настройки, права инструментов, лимит ответа и доступные файлы. Если версия/настройки не раскрываются, записать «неизвестно». Не использовать сведения о модели из ДЗ1 как факт о новом запуске.
4. A получает только базовый промпт и общую основу. B получает ту же основу, улучшенный промпт и явно приложенные три документа. Добавленные инструкции — экспериментальное воздействие; прочие условия должны совпадать.
5. Разрешить по одному запуску без уточняющих запросов и ручных исправлений. Если агент задаёт вопрос или не завершает задачу, сохранить это как результат. Сохранить полный ответ, diff, журнал инструментов и исходные условия.
6. Проверить оба результата по одной рубрике ниже. Для A использовать те же целевые критерии, но отметить, что многие из них не сообщались в базовом запросе. Не исправлять результат до первичной оценки.
7. В обеих копиях запустить одинаковые доступные проверки типов, тестов и сборки; провести клавиатурную проверку и проверку трёх ширин с одинаковыми фикстурами. Дополнительные проверочные тесты оценщика хранить отдельно от исходных ответов и применять одинаково к A/B.
8. Составить список необходимых исправлений, выставить оценки с доказательствами. При желании исправлять результаты — только после сохранения первичного снимка, отдельно фиксируя работу. Не переносить экспериментальный код в основное приложение в рамках ДЗ2.

Одинаковые фикстуры: по книге каждого статуса; finished с rating=null, 1 и 5; notes=null и непустая заметка; title длиной 200 и author длиной 120; заметка с текстом `<script>пример</script>` должна отображаться как текст. Невалидные значения статуса не входят в контракт типизированной карточки.

## Шкалы оценки 1–5

Более высокая оценка означает лучшее соответствие. Для каждой оценки необходимо указать проверенный факт и ссылку на ответ/лог/скриншот. «Не проверено» не равно 1 и не равно 5; это отсутствие оценки.

| Критерий | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- |
| Полнота требований | Основная карточка неработоспособна | Есть название, но отсутствует автор или статус | Название, автор, три статуса есть, необязательные поля/действия неполны | Все основные пункты есть, один небольшой пробел | Все требования B к отображению, контракту и границам соблюдены |
| Типобезопасность | Типов нет или код не компилируется из-за типов | any/строки скрывают ошибки контракта | Типы есть, но Book дублируется или callbacks неточны | Общий Book и точные пропсы; есть одна локальная недоработка | Общий Book, union, точные callbacks, корректный null, проверка типов проходит |
| Читаемость | Код невозможно понять/собрать | Смешаны сеть, UI и действия без необходимости | Работает, но заметно дублирование или неясные имена | Понятная структура с одним небольшим замечанием | Короткий компонент, ясные имена и разделение ответственности, нет лишних абстракций |
| Нестандартные случаи | Обычный допустимый вариант вызывает сбой | Несколько случаев null/длинного текста сломаны | Часть случаев обработана, два и более пробела | Все кроме одного небольшого случая обработаны | null, условная оценка, безопасная заметка и длинный текст проверены и корректны |
| Доступность | Действия недоступны с клавиатуры | Несколько существенных проблем семантики/имён/фокуса | Базовые кнопки работают, но есть два пробела | Один небольшой пробел, основные действия доступны | Семантика, имена, текстовые статусы, клавиатура и фокус проверены |
| Тестируемость | Невозможно проверить контракт или тесты не запускаются из-за результата | Только snapshot/поверхностный тест | Есть содержательные тесты, но нет статусов или callbacks | Проверены статусы и callbacks, один пробел по полям | Все требуемые сценарии карточки покрыты воспроизводимыми проходящими тестами |
| Количество необходимых исправлений | 7 и более | 5–6 | 3–4 | 1–2 | 0 |

Исправление — один независимо проверяемый дефект относительно зафиксированного контракта, а не строка кода или субъективное пожелание. Одну причину не считать несколько раз. Отдельно записать точное число и перечень дефектов. Проверка адаптивности учитывается в нестандартных случаях; доступность оценивается отдельно. Баллы связаны и не являются независимыми метриками.

## Ограничения методики и шаблон выводов

Одна пара запусков не доказывает общую закономерность: генерация вариативна. B одновременно получает больше информации, правила и формат RTCF; отдельно оценить вклад каждого фактора таким экспериментом нельзя. Оценка A по требованиям B показывает полноту постановки, а не способность модели угадать скрытый контракт. Неизвестная версия модели, разные права или отсутствие запуска тестов дополнительно ограничивают сопоставимость. Для более надёжного вывода нужны повторения при тех же условиях.

После проверки заполнить:

> Дата и условия: [факты]. В A наблюдалось [факт + ссылка], в B — [факт + ссылка].
> По критерию [название] оценки составили [A] и [B], потому что [доказательство].
> Число необходимых исправлений: [A] и [B], перечень: [ссылка].
> Гипотеза [поддержана / не поддержана / данных недостаточно] в пределах этих запусков.
> Не проверено: [перечень]. Ограничения: [фактические различия условий].
> Для следующего запроса BookTrack следует [вывод из наблюдений].

До проведения запусков сравнительный вывод остаётся открытым.
