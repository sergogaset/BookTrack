# Пять шаблонов RTCF для BookTrack

[Навигация](README.md) · [Контекст](project_description.md) · [Технические требования](technical_specification.md) · [Правила](rules.md)

RTCF: Role — роль, Task — задача, Context — контекст, Format — формат ответа. Ниже ровно пять шаблонов. В универсальной версии замените переменные в квадратных скобках фактическими значениями. Примеры предназначены для будущих этапов; в ДЗ2 выполнять их не требуется. Пути реализации агент определяет после изучения репозитория. Если frontend ещё отсутствует, следует сообщить о недостающей основе, а не создавать всё приложение в рамках одной компонентной задачи.

## 1. Анализ требований и планирование функциональности

Назначение: превратить запрос на функцию BookTrack в ограниченный и проверяемый план ДЗ3.

### Универсальная версия

```text
R — Role: Ты системный аналитик учебного проекта BookTrack.
T — Task: Проанализируй функцию [функция] на этапе [этап]. Выдели
пользовательские сценарии, требования и критерии приёмки; код не меняй.
C — Context: Прочитай [документ контекста] и [правила]. Исходный запрос:
[запрос владельца]. Текущая реализация: [факты о репозитории].
Границы: [разрешённый объём]; исключено: [исключения].
Отдели подтверждённые факты от допущений. Вопросы задавай только
при противоречии, которое блокирует постановку задачи.
F — Format: Краткое описание проблемы; таблица требований с ID;
сценарии и проверяемые критерии; допущения; план 5–7 шагов;
проверки и итоговое резюме. Не раскрывай внутреннюю цепочку рассуждений.
```

### Заполненный пример BookTrack

```text
R — Role: Ты системный аналитик BookTrack.
T — Task: Для ДЗ3 уточни поиск по названию/автору и фильтр статуса,
составь план будущей реализации. Файлы не изменяй.
C — Context: Прочитай docs/project_description.md, docs/technical_specification.md и docs/rules.md.
В репозитории пока только документация; проверь актуальное состояние.
Основа — FR-06 и FR-07. Поиск: вхождение без регистра, trim запроса;
фильтр: «Все», want_to_read, reading, finished; совместное применение AND.
Пустая библиотека и отсутствие совпадений различаются. В ДЗ4 — mock data.
Не добавляй жанры, внешние API, нечёткий поиск, сервер или авторизацию.
F — Format: Проблема; таблица уточнений FR-06/FR-07; сценарии с Given/When/Then
для поиска, комбинации фильтра, сброса условий и отсутствия совпадений;
явные допущения; план 5–7 шагов и проверки; краткое резюме.
```

Качество: требования проверяются конкретными входами и результатами; AND указан явно; нет новых функций MVP; план соответствует mock-этапу и не выдаёт его за выполненную работу.

## 2. Разработка React-компонента карточки книги

Назначение: получить небольшой компонент отображения с типизированным контрактом на ДЗ4.

### Универсальная версия

```text
R — Role: Ты frontend-разработчик React и TypeScript проекта BookTrack.
T — Task: Создай или дополни [компонент карточки] в пределах [объём].
C — Context: Изучи [контекст], [правила], [связанные файлы].
Данные: [тип книги]; пропсы: [контракт]; поля отображения: [поля].
Действия: [действия]; ограничения UI: [адаптивность и доступность].
Не добавляй сеть, новые зависимости и функции вне MVP.
Если нет основы frontend, сообщи, что требуется, и не создавай приложение.
F — Format: Найденные файлы и допущения; краткий план; минимальные изменения;
тесты [сценарии]; фактические проверки и итоговое резюме с ограничениями.
```

### Заполненный пример BookTrack

```text
R — Role: Ты frontend-разработчик React + TypeScript BookTrack.
T — Task: В готовой основе ДЗ4 создай BookCard для отображения одной книги.
C — Context: Прочитай docs/project_description.md, docs/technical_specification.md и docs/rules.md;
примени RULE-01–RULE-05 и RULE-08–RULE-13. Сначала проверь наличие frontend.
Используй общий Book ДЗ4 (без user_id), не дублируй его; BookStatus — union
want_to_read | reading | finished. Props: book: Book,
onEdit: (id: string) => void, onDelete: (id: string) => void.
Покажи title, author, русскую подпись status, rating только для finished
и ненулевой оценки; пустую notes не показывай, непустую выводи текстом.
Кнопки «Редактировать» и «Удалить» только вызывают callbacks с id;
подтверждение удаления выполняет родитель. Используй article с заголовком,
button type=button, доступные имена с названием книги, видимый фокус.
На 320/768/1280 px текст переносится без переполнения. Tailwind CSS,
никаких обложек, API и новых зависимостей. Loading/error/empty списка — у родителя.
F — Format: Краткий план и допущения; минимальный diff; тесты всех трёх подписей,
условий оценки/заметки и callbacks с правильным id; результат доступных проверок,
отдельно ручная проверка адаптивности; итоговое резюме.
```

Качество: нет any и дубликата Book; три подписи точны; callbacks не изменяют хранилище; длинные поля не ломают карточку; тесты проверяют наблюдаемое поведение.

## 3. Создание формы добавления/редактирования книги

Назначение: задать общий контракт формы с валидацией и mock-сохранением.

### Универсальная версия

```text
R — Role: Ты frontend-разработчик доступных форм BookTrack.
T — Task: Реализуй [форма] в режимах [режимы].
C — Context: Изучи [контекст], [правила], [существующие формы/типы].
Поля и ограничения: [перечень]. Контракт: [начальные значения и callbacks].
Сохранение: [mock или существующий слой]; состояния: [поведение].
Отмена: [поведение]; исключения: [границы этапа].
F — Format: Контракт и допущения; краткий план; минимальный diff;
проверки валидности, успеха, отказа и отмены; фактические результаты и резюме.
```

### Заполненный пример BookTrack

```text
R — Role: Ты frontend-разработчик React + TypeScript BookTrack.
T — Task: В основе ДЗ4 создай переиспользуемую BookForm для добавления
и редактирования с начальными значениями; не подключай Supabase.
C — Context: Прочитай docs/project_description.md, docs/technical_specification.md и docs/rules.md.
Сначала изучи типы и компоненты. Поля: title (trim, 1–200), author
(trim, 1–120), status (want_to_read/reading/finished), rating (null либо
целое 1–5 только при finished), notes (trim, до 1000; пустая -> null).
Контракт: initialValues?: BookInput, onSave(input: BookInput): Promise<void>,
onCancel(): void. BookInput содержит только пять редактируемых полей;
при редактировании родитель связывает onSave с id и сохраняет created_at.
Для новой книги статус want_to_read, rating/notes null. При смене finished
на иной статус очисти rating до null с пояснением. Ошибки свяжи с label/полями,
переведи фокус к первому неверному полю. При pending заблокируй повтор
и отмену; при reject сохрани ввод и разреши повтор/отмену. На resolve родитель
закрывает форму и объявляет успех. До отправки отмена ничего не сохраняет.
Используй существующие UI и Tailwind, без новых зависимостей; проверь 320/768/1280 px.
F — Format: Контракт и краткий план; минимальные изменения; тесты валидации,
смены статуса, pending, resolve, reject и отмены; фактические команды/результаты,
ограничения и резюме. Если основы нет, только сообщи о недостающем контексте.
```

Качество: добавление и редактирование используют одну валидацию; null не превращается в 0; служебные поля не редактируются; ошибка не теряет ввод; успех не объявляется до resolve.

## 4. Генерация автоматических тестов

Назначение: проверить пользовательское поведение существующей функции ДЗ4.

### Универсальная версия

```text
R — Role: Ты инженер по тестированию BookTrack с Vitest и React Testing Library.
T — Task: Добавь тесты для [функция/компонент] по [требования].
C — Context: Изучи [код], [контекст], [правила] и существующую конфигурацию.
Инструменты: [доступные инструменты]. Проверь [сценарии и границы].
Используй детерминированные mock data и проверяй UI/контракты, а не внутренний state.
Не подключай реальные сервисы и не устанавливай зависимости.
F — Format: Таблица «требование — сценарий — ожидание»; тестовый diff;
команда и фактический результат запуска; выявленные дефекты и непроверенное.
Если окружения нет, укажи это и дай план без заявления об успешном запуске.
```

### Заполненный пример BookTrack

```text
R — Role: Ты инженер по тестированию BookTrack, Vitest + React Testing Library.
T — Task: Добавь тесты BookForm для FR-02, FR-08, FR-09.
C — Context: Прочитай docs/project_description.md, docs/technical_specification.md, docs/rules.md и существующую
BookForm с её типами и тестовой конфигурацией. Код формы без необходимости не меняй.
Проверь: пробельный title/author блокирует onSave; границы длины 200/201,
120/121, 1000/1001; rating null и 1/5 допустимы при finished, 0/6/дробь запрещены;
смена finished -> reading очищает rating; успешный onSave получает нормализованный
BookInput один раз; управляемый Promise блокирует повтор/отмену; reject сохраняет
ввод и показывает ошибку; отмена до отправки вызывает только onCancel.
Используй доступные label/role, имеющиеся средства пользовательских событий,
mock Promise без реальной сети и произвольных задержек. Не устанавливай зависимости.
F — Format: Матрица покрытия; минимальный тестовый diff; точная команда запуска
из существующих scripts и результат. Если конфигурации/компонента нет — перечень
недостающего и план. Не называй написанные, но не запущенные тесты пройденными.
```

Качество: тесты воспроизводимы, покрывают отрицательные случаи и асинхронный отказ; нет зависимости от CSS-классов; отчёт отличает запуск от статического анализа.

## 5. Анализ ошибки и безопасный рефакторинг

Назначение: локализовать дефект и внести ограниченное исправление с доказательствами.

### Универсальная версия

```text
R — Role: Ты разработчик BookTrack, выполняющий безопасную диагностику.
T — Task: Найди и исправь [наблюдаемая ошибка]; при необходимости выполни
минимальный рефакторинг, сохраняющий [контракты].
C — Context: Прочитай [контекст/правила/файлы]. Воспроизведение: [шаги].
Ожидание: [результат]; факт: [результат/лог]. Ограничения: [границы].
Раздели наблюдения и гипотезы; не выполняй разрушительные действия.
F — Format: Краткая диагностика с проверяемыми свидетельствами; план;
регрессионный тест; минимальный diff; фактические проверки и остаточные ограничения.
Если дефект не воспроизводится, сообщи об этом, не заявляя об исправлении.
```

### Заполненный пример BookTrack

```text
R — Role: Ты React/TypeScript-разработчик BookTrack, выполняющий диагностику.
T — Task: Проверь учебный сценарий ошибки: после reject mock-сохранения
BookForm очищает title и author. При подтверждении исправь потерю ввода.
C — Context: Это гипотетический сценарий для будущего ДЗ4, не обнаруженный
дефект текущего репозитория. Прочитай docs/project_description.md, docs/technical_specification.md и docs/rules.md,
затем код формы и тесты, если они существуют. Воспроизведение: ввести «Мастер
и Маргарита», «Михаил Булгаков», выбрать reading, отправить, отклонить mock Promise.
Ожидается: поля сохранены, ошибка объявлена, повтор и отмена доступны.
Сохрани контракт onSave(input): Promise<void> и onCancel, публичные пропсы
и нормализацию BookInput. Не меняй список, БД, зависимости или пользовательские
документы; не делай массовый рефакторинг. Сброс допускается после успеха.
F — Format: Наблюдения и гипотезы; краткий проверяемый план; регрессионный тест
reject и контроль успешного сценария; минимальный diff; команды и фактические
результаты; резюме. Если кода нет или проблема не воспроизведена, честно укажи это.
```

Качество: причина подтверждается кодом/тестом; исправление локально; успешное сохранение не сломано; гипотеза не представляется наблюдением; разрушительных действий нет.
